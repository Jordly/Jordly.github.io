## 📋 CS CloudHub "完善与落地方案" 制定（架构师高见远产出）

用户要求以架构师/软件工程专家身份，为系统制定系统性完善方案，四大块：优化切入点识别、改动执行顺序、测试方案、可量化指标。

**已核查的系统现状（重要事实）**：
- 纯原生 JS 单页应用，无框架、无构建、无测试
- `app.js` 13135 行 / 664KB 巨型单文件（版本 20260723）
- `style.css` 2560 行；另有 dark-mode.css、premium-enhancements.js、filterBarNew.js
- 数据：Mock + localStorage + CloudBase 云函数（csCloudHubAPI）同步
- 部署：GitHub Jordly.github.io 根目录 → Cloudflare Pages（chanseen.pages.dev）

**方案核心结论**：
- 最大风险不是性能，而是"数据丢失 + 出错不可见"
- 5 阶段路线：P0 数据安全网（一键备份+恢复演练）→ P1 可观测性（全局错误捕获+运行日志+云同步状态）→ P2 热点与安全修复（分页/写合并/异常补全/PBKDF2）→ P3 测试基线（自研 test.html + core-math.js 提取）→ P4 结构治理（可选）
- ROI 公式 =（影响面×风险）÷ 成本，排序筛选切入点
- 指标：启动耗时≤3s、500条列表≤1s、错误数/日≤3、云函数失败率≤5%、核心计算覆盖率≥80%、app.js 行数不增
- 健康分加权：性能30%+错误30%+覆盖20%+安全20%

**交付物**：`CS-CloudHub-完善与落地方案.md`（项目根目录，本地未推送）

**注意事项**：docs/ 和根目录都是部署源（Jordly.github.io 公开仓库），方案文档未 commit/push，仅本地保留，避免公开。

## 🟡 黄灯修复

### 黄灯6：数据安全铁律（不动代码）
- 在 MEMORY.md 建立铁律：代码只放假数据，真实数据仅存 localStorage
- 规则：所有 DEFAULT_* 数组只能含虚拟数据；真实客户/员工信息不得写入代码

### 黄灯4：密码升级 PBKDF2
- app.js hashPassword：SHA-256 → PBKDF2（加盐+10万次迭代）

- login.html 验证逻辑：支持 $PBK2$（新）/ $SHA$（老自动升级）/ 明文（老自动升级）三种格式
- 用户登录成功时自动将旧密码哈希迁移为 PBKDF2，无感知
