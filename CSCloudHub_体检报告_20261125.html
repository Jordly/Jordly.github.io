P0 · 严重问题（建议优先处理）

共 4 项安全 + 1 项功能
P0-1

"查看演示"按钮 = 免密超级管理员后门

现象：任何人打开网站首页，点一下"🎬 查看演示"，无需密码直接进入系统。
证据：index.html:347 的按钮调用 demoLogin()（app.js:1660）：它不校验任何密码，直接写入 chanseen_auth。而 checkLogin()（app.js:1146-1164）拿到 token 后，用 USERS.find(...) || USERS[0] 兜底——USERS[0] 正是超级管理员账号，于是 currentRole 被设为"超级管理员"。
影响：外部访客可查看/导出全员花名册、绩效、成本数据，甚至修改权限、删除记录。这是全站最危险的入口。
建议：若演示仅用于对内讲解，直接删除该按钮或改为只展示静态截图；若必须保留，需服务端签发"只读、限时、数据脱敏"的演示会话，并禁止访问 systemData / permissions / 导出功能。
P0-2

默认账号口令哈希硬编码，且用户改不掉密码

现象：两个内置账号的密码哈希写死在前端 login.html 里，且用的是单轮无盐 SHA-256（可被现成彩虹表秒级还原）。
证据：login.html:1102-1105 的 defaultUsers 数组含 $SHA$ 前缀哈希；login.html:1118 存在"每次登录都把用户改过的密码重置回默认值"的逻辑（savedUsers[foundIdx].password = defaultUsers[di].password）；login.html:1192-1208 还保留明文比较分支。
影响：默认口令永久有效、无法通过界面真正修改；哈希公开在源码里，懂行的人可直接还原。（本报告刻意不写出任何明文口令。）
建议：上线前从前端移除 defaultUsers；删除第 1118 行的强制复位；把旧 $SHA$ 一次性迁移为加盐 PBKDF2（项目已有 core-security.js 的 PBKDF2 实现，可直接复用）。
P0-3

登录凭证与权限纯前端校验，可一行代码绕过

现象：token 是 'demo_'+Date.now() 这种无签名字符串，权限判断只在浏览器内存里做。
证据：login.html:1212-1227 生成 token；app.js:1146-1172 只要 token 在 1 小时内就直接以管理员身份登录；app.js:2605-2624 的 getPermission、modules/assessment.js:784-816 的 filterNavByPermissions 仅做 style.display='none'。
影响：在浏览器控制台执行一段 JS 就能伪造超级管理员身份；把隐藏的菜单改回可见即可访问受限功能。数据本身也都在 localStorage，可被直接读取。
建议：纯静态站点无法真正做安全鉴权。最低成本方案：在 Cloudflare 侧启用 Cloudflare Access 做整站身份认证（邮箱/OTP），把整个应用挡在网关后；前端权限隐藏只保留为"体验优化"，不再当作安全边界。彻底方案是认证与数据接口下沉服务端。
P0-4

云同步密钥前端明文 + 云函数通配符跨域（当前休眠，开启即高危）

现象：云函数共享密钥写死在前端代码里，云函数允许任意域名调用。
证据：cloudbase-sync.js:18 的 AUTH_TOKEN = 'cscloudhub-2026-secret-key'；cloudbase-api/index.js:110-112 等处 Access-Control-Allow-Origin: '*'；cloudbase-api/index.js:327 连含密码哈希的用户表一起同步。
影响：目前 OFFLINE_MODE = true，链路休眠所以暂未暴露。但代码注释里就写着"如何开启"——一旦开启，任何网站拿这个公开密钥就能读写你的全部云端数据。
建议：开启云同步前必须先做：密钥移入云函数环境变量、CORS 收紧为 https://chanseen.pages.dev、禁止同步 users 集合、改用 CloudBase 自定义登录按用户身份授权。
P0-5

目标数据"两份数据源"互相覆盖（功能性数据缺陷）

现象：在"目标与权责管理"页新增的目标，到"系统数据管理→目标与权责表"看不到；反过来在系统数据管理里改，又会把前者覆盖。
证据：app.js:598 定义 var GOALS；goal-management.js:3 又定义一次 var GOALS（后加载，覆盖前者）。modules/systemData.js:275 的 goals 表绑定的是 app.js 那份数组对象；goal-management.js:18-23 的 saveGoals() 只写 localStorage、不回写 systemData 的数组。_saveSystemData('goals') 用旧数组写回 localStorage，直接覆盖新数据。
影响：两个页面各存各的、互相覆盖，刷新也不会自愈。这是上次 8-18"补 GOALS 数据源"时引入的重复定义，属于本轮体检新发现。
建议：收敛为单一数据源：删除 goal-management.js 的 var GOALS，让它引用 app.js 的全局 GOALS；两处保存都走同一个 saveGoals()，并让 systemData 的 goals 表直接读同一对象。改前需你确认保留哪套页面结构。

P1 · 高危问题

可被利用或明显影响使用
P1-1

多处 XSS 注入点（导入文件 / 花名册 / 满意度详情）

证据：① project-import-export.js:245/248/259 把 CSV/Excel 里的人员名称直接拼进 innerHTML；② modules/roster.js:384 的 infoItem() 中 +v+ 未转义（同文件其他地方都用了 esc()，此处明显遗漏）；③ modules/satisfaction.js:363-451 详情模板里 ${s.xxx} 大片未转义；④ modules/notifications.js:171 把注册姓名 ${user.name} 直接拼进管理员弹窗。
影响：若有人通过导入功能写入带脚本的"姓名/项目名"，管理员打开预览或详情时脚本就会执行，可能外带 localStorage 里的全员数据。
建议：统一给这些插值包上项目已有的 escHtml()（core-security.js:5）；导入落库前对字段做清洗。好消息：escHtml 全项目只有一处定义、且加载顺序正确，不存在被覆盖的问题，转义基础设施是可靠的。
P1-2

第三方库浮点版本 + 全站无 CSP

证据：index.html:220 引用 cdn.sheetjs.com/.../xlsx-latest/....js——"latest"是浮动版本，且无 SRI 校验、无 crossorigin；全站无 Content-Security-Policy。该库正好用于解析用户上传的 Excel。
建议：锁定具体版本号并加 integrity 哈希，优先把文件下载到站点自托管；用 Cloudflare 的 _headers 文件加一道 CSP。另：index.html:60-66 注入了 Microsoft Clarity 外部统计，内部系统建议确认是否符合公司数据合规要求。
P1-3

管理员新增/重置密码的输入框是明文

证据：modules/notifications.js:283 的密码输入框写的是 type="text"，密码直接显示在屏幕上。
建议：改为 type="password"，一行改动、零风险。项目里 app.js:1655 已有 togglePwd() 显示/隐藏密码的实现，可复用加个"小眼睛"。
P1-4

"大促预案"模块是孤儿——代码写了但用户点不到

证据：modules/eventPlan.js（22KB，基于大促指导手册）在 index.html:231 被加载，但侧边栏无菜单、app.js:2439 的模块清单无它、app.js:2958 的渲染分发表也无它；文件内 renderModule('eventPlan') 调用会掉进"模块开发中"兜底。
影响：对电商客服总监，大促预案是高频刚需，却被"藏"起来了；同时这段代码属于死代码，增加维护负担。
建议：二选一——要么在"项目运营"分组加一个菜单入口并接入渲染分发；要么确认已弃用后彻底删除该文件及其脚本引用。
P1-5

提示方式不统一：76 处 alert + 三态组件调用率低

证据：全项目 alert( 共 76 处，而项目其实已提供体验更好的 showToast()（app.js:234）和空/加载/错误三态组件（app.js:196-231，带骨架屏和刷新按钮）。三者在各模块中混用，例如 handover 用 alert、assessment 用 Toast、knowledge 用无类型 Toast。
建议：不必一次全改。先统一"新增/编辑"这类高频表单的必填校验（改 alert 为 showToast(msg,'error')' + 字段红框），其余逐步收敛。
